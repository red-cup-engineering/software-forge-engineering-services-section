# Community evidence enters the source forge

The `./community-work-order` and `./community-source-candidate` exports connect
the original Social Publication evidence interpreter to the original Software
Forge candidate and downstream Git Forge. They create no second work store,
code producer, platform transport or source identity scheme.

```js
const order = communityWorkOrder({
  assessment, requirementId, workRef,
  target: { repository, commitSha, path, blobSha },
});
const proposed = synthesizeCommunitySourceCandidate({
  workOrder: order, artifact, signcraftSource,
  ctx, basis, complex, valuation,
});
// The established Git Forge consumes proposed.candidate with its exact Git target.
```

`communityWorkOrder` checks the assessment's native content address and replays
its observations and declared requirements through the original interpreter.
Only a `denied` requirement can become this repair input. Unknown data requires
observation; contested data requires reconciliation; already held requirements
do not create invented missing-feature work. A caller cannot relabel a result
as denied and gain source-work admission merely by recomputing its hash.

The target retains a repository, full commit SHA, intended relative path and
prior full blob SHA or explicit `null` for caller-declared absence. A source
observation naming a different repository refuses. The actual Git source reader
and provider must still qualify the target against current source. This pure
function does not manufacture proof that a file is absent or reserve a writer.

Source work must also have an actual source relationship. README, CONTRIBUTING
and license requirements admit their corresponding recognized repository paths.
Provider metadata, topics, counters and activity observations remain with the
provider effect owner even if a caller attaches an arbitrary source declaration.
Other source requirements must explicitly declare `sourceContract` with
`{kind:'repository-file', path, role}`; the target must match that authored path.
This declaration allocates a machine obligation and does not prove a world result.

The order carries the original Work reference, stable requirement id, requirement
definition and evaluation Cell addresses, source evidence Cells, and the exact
input assessment needed for portable replay. It names the later acceptance
operation: reobserve the same subject and predicate under the same requirement
and receive a held reading. Source compilation or a nominally complete
construction cannot discharge that receiving condition.

`communitySourceCandidate` accepts a separately produced artifact and bounded
SignCraft construction, checks that they target this order and requirement, and
calls the existing `forgeSourceCandidate`. The resulting `candidate` keeps the
established `software-forge.source-candidate.v1` shape, including actual code
bytes, their SHA-256 digest, the declared producer source and original Work.
Its surrounding native Cells preserve the requirement-to-candidate relation.
The existing Git Forge owns branch/ref binding and the existing GitHub owner
owns authenticated file, branch and pull-request effects.

`synthesizeCommunitySourceCandidate` performs the genuine original SignCraft
`synthesize` call before that boundary. The caller supplies the admitted finite
context and valuation; the operation fixes the synthesis object to this work
order and requires the exact requirement definition attribute. The construction
is explicitly counterfactual. A supplied reference context is not evidence that
a generated artifact has already changed a repository or met a market need.

Code generation stays with the existing Code owner, such as its
`renderJsonSchemaModule` operation. No placeholder code is generated by this
bridge. Declared producer provenance, local verification, Git receiving,
installation and reobservation remain separate evidence obligations.
